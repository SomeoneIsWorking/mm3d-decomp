## The finding that shapes everything below: `.text` is NOT partitioned by module

MM3D's code is not laid out as one contiguous address block per source file, so
"which module is this address in" is not a well-posed question for most addresses.
Three independent measurements, all reproducible from this repo:

1. **A single file's own functions can be megabytes apart.** Of the 92 source files we
   can attribute, 14 have attributed functions more than 256 KiB apart. `Package.cpp`
   anchors at `0x0012cb6c` and `0x005c5a5c` — 4.82 MB apart, same translation unit.
2. **Link order in `.rdata` does not predict link order in `.text`.** Sorting the 92
   files by their first assert string in `.rdata` and sorting them by their first
   anchored function in `.text` gives 2061 inversions out of 4186 pairs — 50.8%
   monotone agreement, i.e. chance. A linker that emitted TUs contiguously in both
   sections would score near 100%.
3. **Function addresses inside one file are interleaved with other files'.**
   `z_play.cpp` anchors at `0x0012a7d4` and `0x00551fb8`; `ActorMultiEffect.cpp` has
   six anchored functions spread from `0x001581c0` to `0x005efd18`.

Consequence: **the module organization is a function -> source-file assignment, not an
address partition.** The table below is therefore an address bucketing for *planning*
(you can say "this address neighbourhood contains Player code"), and a row is named
ONLY when an assert-path string proves at least one function in that row is defined in
that file. The other functions in a named row are **not** attributed.

## Evidence rule, and the one inference that is rejected

MM3D's asserts embed the build machine's own source paths, e.g.
`C:\Jenkins\workspace\joker\prog\game\sources\main.cpp(344)`.

The compiler materialises such a string with an ARM `LDR rX, [pc, #imm]` whose literal
pool word *is* the string address. Decoding every such instruction over the whole image
and mapping it back to its containing function is therefore a direct, ground-truth
attribution: **the function that loads `...\z_kankyo.cpp(1889)` is, by the developers'
own construction, in `z_kankyo.cpp`.** No fingerprint, no guess.

`source_files.csv`'s `string_va` column is the offset of `<file>.cpp(<line>)` *inside*
the path, not the head of the path — the head is 45-63 bytes earlier (it depends on the
sub-directory: `sources\`, `sources\original\`, `sources\hid\menu\state\`, ...), and
the compiler points at the head. Both must be in the accepted set or every search
returns zero and the tool reports a confident, wrong "no references".

**Rejected inference.** Allowing a second pointer hop (pool word -> a `.data` word ->
the string) produced 2 extra "attributions", and both are wrong:

| LDR at | pool | data word | would claim | why rejected |
|---|---|---|---|---|
| `0x00204960` | `0x00204a84` | `0x0068d6cc` -> `0x00646400` | `z_oceff_storm.cpp(533)` | `FUN_00204640` is `Player_Update`, pinned by the `play->playerUpdate` handler-pointer table in `docs/player_port.md`. `0x00646400` is the shared path *prefix* of the next assert string, so a deep chain lands on an adjacent string by coincidence. |
| `0x00552ad0` | `0x00552bb0` | `0x00678528` -> `0x00646464` | `z_play.cpp(3140)` | same failure mode; not used, even though the surrounding functions are plausibly `z_play.cpp`. |

Only direct one-hop references are used below.

`helper1` is an inference, not a fact: a file's static helper is usually in the same
translation unit, but a small shared utility can also be the only callee of an anchor.
It is kept separate for that reason, and callers of an anchor are deliberately NOT
counted (everything in the engine goes through the GAR2 reader, so counting its callers
would hand `ObjectBankArchive.cpp` 171 phantom functions).
